# MANDARA進化構想 — フラクタル思考エンジンへの設計プラン

> 前提ドキュメント: [ADOPTION_UX_ANALYSIS.md](./ADOPTION_UX_ANALYSIS.md)(定着分析)
> 本書は「思考展開を自由にする」ためのMandara拡張 — AI自動分類インポート、親子フラクタル構造、
> 可変グリッド、キャンバス/ホワイトボードモード — のアイデア展開・定義・実現性評価・実装プラン。

---

## 0. ビジョン: 「9マスのフォーム」から「思考のフラクタル空間」へ

現行のMandaraは「9個のtextareaを持つ1枚のフォーム」(`js/mandara-logic.js:13-35`)。
目指す姿は次の3公理で定義できる:

1. **思考はフラクタルである** — どのマスも、それを中心とした新しいマンダラに展開できる(ズームイン)。
   どのマンダラも、より大きな構造の1マスに位置づけ直せる(ズームアウト)。深さに制限はない。
2. **思考は外から来る** — Markdown・Webページ・貼り付けテキストを、AIが「中枢の判定+マスへの分類」
   を行ってマンダラ化できる。逆にマンダラツリーは常にMarkdownとして外へ出せる(双方向性)。
3. **思考は枠に先立つ** — 枠(グリッド)は思考を整理する「ビュー」であって「容れ物」ではない。
   枠のない自由配置(ホワイトボード)から始めて、後から構造化してもよい。

この3つが成立すると、「発散(ホワイトボード)→ 収束(マンダラ分類)→ 深掘り(子展開)→
実行(TODO/ガレージ連携)→ 発信(Publish/エクスポート)」という思考のフルサイクルがアプリ内で閉じる。

## 1. データモデル v2 — すべての基盤

### 1.1 現状の制約

現行スキーマ(`js/mandara-logic.js:13-35`, FIRESTORE_DB_STRUCTURE.md):

```js
{ id, title, cells: {1..9: string}, memo, tags, todos, linkedGarageId, createdAt, updatedAt }
```

- セルが**ただの文字列**のため、子リンク・タグ・状態・座標など一切のメタデータを持てない
- 9マス固定がスキーマに焼き付いている(`cells: {1..9}`)
- 親子関係を表すフィールドがない(`linkedGarageId` と同様のデッドエンドを増やさないため、
  「書くだけで読まれないリンク」は絶対に作らない — 双方向で必ず読む)

### 1.2 提案スキーマ: Board / Grid / Cell / Node

**用語定義**

| 用語 | 定義 |
|---|---|
| **Board** | 1つの思考空間の最上位単位(現行の「マンダラ1件」に相当)。ツリー全体のルート |
| **Grid** | Board内の1枚のマス目構造。中心セル+周辺セル。Boardは複数Gridのツリーを持つ |
| **Cell** | Grid内の1マス。テキスト+メタデータ+(任意で)子Gridへの参照 |
| **FreeNode** | ホワイトボードモードで自由座標に置かれる付箋ノード(Gridに属さない) |

**スキーマ(Firestore: `users/{uid}/boards/{boardId}`)**

```typescript
interface Board {
  id: string;
  schemaVersion: 2;              // マイグレーション判定用
  title: string;
  rootGridId: string;            // ツリーのルートGrid
  grids: Record<string, Grid>;   // Boardに属す全Grid(埋め込みMap)
  freeNodes: FreeNode[];         // ホワイトボードモードのノード
  memo: string;
  tags: string[];
  todos: Todo[];                 // 既存構造を踏襲
  linkedGarageIds: string[];     // 双方向表示前提(片方向デッドエンド禁止)
  viewState: {                   // 端末ローカルでもよいが同期すると便利
    mode: "fit" | "canvas" | "board";
    camera?: { x: number; y: number; zoom: number };
    focusGridId?: string;
  };
  createdAt: Timestamp;
  updatedAt: Timestamp;
}

interface Grid {
  id: string;
  pattern: "3x3" | "2x2" | "4x4" | "1xN" | "radial8";  // §3 可変パターン
  centerCellId: string;
  cellIds: string[];             // 表示順(中心含む)。1xNでは可変長
  parentCellId: string | null;   // 親Gridのどのセルから展開されたか(null=ルート)
  cells: Record<string, Cell>;
  position?: { x: number; y: number };  // キャンバスモードでのGrid配置
  collapsed?: boolean;           // 展開ビューでの折りたたみ
}

interface Cell {
  id: string;
  text: string;
  childGridId: string | null;    // このセルを中枢として展開した子Grid
  tags?: string[];
  status?: "idea" | "active" | "done";   // 将来のTODO/レビュー連携用
  source?: { type: "manual" | "ai-import" | "whiteboard-promote"; ref?: string };
}

interface FreeNode {
  id: string;
  text: string;
  x: number; y: number;          // キャンバス座標(論理px、zoom非依存)
  w?: number; h?: number;
  color?: string;
  groupId?: string;              // AIグルーピング結果の暫定グループ
}
```

**設計判断とその理由**

- **Grid群はBoardドキュメントに埋め込む**(サブコレクションにしない)。
  1回のreadでツリー全体をロードでき、既存の `storage-service.js` のJSON保存
  (`js/storage-service.js:154-171`)と同じ形で動く。Firestoreの1MB/doc制限は、
  テキスト主体なら数百Grid相当まで余裕(1Grid≒1〜3KB)。超大型Board対策は
  将来 `grids` のみサブコレクション化する逃げ道を残す(スキーマ上はMapなので移行容易)。
- **親子は双方向参照**(`Cell.childGridId` ⇄ `Grid.parentCellId`)。片方向リンクの
  デッドエンド化(`linkedGarageId` の轍)を避け、整合性チェック関数を `mandara-logic.js`
  相当の純関数層に置いてテスト対象にする。
- **座標はGrid/FreeNodeに持たせ、ビューには持たせない**。fitモードは座標を無視して
  レイアウトし、canvasモードだけが座標を使う — 同一データで両ビューが成立する。

### 1.3 マイグレーション(v1→v2)

読み込み時に `schemaVersion` 欠如を検出したら純関数で変換(不可逆な破壊はしない):

```
v1.cells[1..9] → rootGrid(pattern:"3x3") の cells に写像(5番→centerCell)
v1.memo/tags/todos/title → Board 直下へ
linkedGarageId → linkedGarageIds: [id] (nullなら [])
```

- 変換は**初回保存時に確定**、それまではメモリ上のみ(読み取り専用ユーザーを壊さない)
- `mandara-logic.js` を `board-logic.js` として再編し、新旧両スキーマのユニットテストを先に書く
- 未使用の `mandara-store.js`(Pub/Subストア、現在デッドコード)を**この機会に本採用**。
  ツリー+キャンバスはグローバル変数の手管理では破綻するため、Store一元管理が前提条件

**実現性: 高。** 既存データ量は個人利用規模で、変換は純関数1本。最大リスクはUI側の
`mandara.js`(951行)がv1スキーマ直参照している点で、Store経由アクセスへの書き換えが実質の工数。

## 2. 親子フラクタル構造 — ズームイン/ズームアウト

### 2.1 ズームイン(子展開)

**UX**: セルにホバー/フォーカスすると「展開 ⤵」アクション表示 →
クリックで `childGridId` の子Gridを生成(セルのテキストが子Gridの中心セルに**参照コピー**)し、
ビューがその子Gridへ遷移。パンくず(`ルート > 健康 > 運動習慣`)で任意階層へ戻れる。

**中心セルの同期問題**(重要な設計点): 子Gridの中心テキストと親セルのテキストは
「同一の思考」なので、**単方向同期: 親セルが正、子の中心は親セルを表示するだけ**
(子中心を編集したら親セルに書き戻す)。二重データを持たせないことで矛盾を構造的に排除する。
実装は `Cell.childGridId` を持つセルの編集ハンドラで親子両方を更新するだけ。

### 2.2 ズームアウト(親の創出)

「いま見ている9マスは、実はもっと大きな構造の1マスだった」という気づきを操作にする:

**UX**: ツールバー「⤴ 親構造を作る」→ 新しいGridが生成され、現在のGridの中心テキストが
新Gridの**周辺セルの1つ**に入り、新Gridの中心は空(または AI が候補提案 §4)。
データ操作は単純: `newGrid.cells[k].childGridId = currentGrid.id`、
`currentGrid.parentCellId = newGrid.cells[k].id`、`board.rootGridId = newGrid.id`。

ルートの付け替えだけで済むのは、ツリーをBoard内に閉じているため。**実現性: 高。**

### 2.3 ナビゲーションと全体把握

- **パンくずリスト**(必須・小コスト)
- **ツリーミニマップ**: 既存 `js/minimap.js`(16ノートのグリッド俯瞰)の設計を流用し、
  Boardツリーをインデント付きリスト or 放射ツリーで表示、クリックでジャンプ
- **展開ビュー(=本家81マス)**: 3×3の各セルの子Gridをその場に展開描画すると、
  古典的マンダラチャート(9×9=81マス)が**特別実装なしで導出される**。
  つまり「81マス対応」は独立機能ではなく、フラクタル構造の1ビュー(§5 canvasモードの
  `expandDepth: 1` 描画)として自然に手に入る。深さ2以上の展開はcanvasモード専用

### 2.4 無限再帰への安全弁

- 深さ制限は設けない(思想に反する)が、**循環参照だけは禁止**(展開時に祖先チェック)
- 削除は「子Gridごとアーカイブ」(ソフトデリート)。フラクタルでは1操作の破壊範囲が
  大きくなるため、ADOPTION_UX_ANALYSIS.md ★1 のアーカイブ思想をここでも適用

## 3. 可変グリッドパターン

`Grid.pattern` により同一エンジンで複数の型を描画:

| パターン | マス数 | 用途 | 備考 |
|---|---|---|---|
| `3x3` | 9 | 標準マンダラ | 現行互換・デフォルト |
| `2x2` | 4+中心なし or 中心+4 | **4STROKESブリッジ**: Key/Issue/Action/Publish | ガレージ⇄マンダラ相互変換の要(後述) |
| `4x4` | 16 | 網羅系ブレスト | fitモードでは文字が小さくなるためcanvas推奨 |
| `1xN` | 可変 | リスト/アウトライン型 | 「まだ構造が見えない」段階の受け皿 |
| `radial8` | 中心+8放射 | マインドマップ的表示 | 3x3と同データ・描画のみ差し替え(低優先) |

- 実装はCSS Grid の `grid-template` をパターン別に切り替えるだけで、データは `cellIds` の
  可変長配列が吸収する。**実現性: 高**(描画層の分岐のみ)
- **パターン変換**(3x3→1xN 等)は「セルの並び替え+余剰/不足の扱い」を確認モーダルで提示
- `2x2` パターンを「Key/Issue/Action/Publish」プリセットにすると、**ガレージ=2x2 Grid** という
  統一が可能になり、ADOPTION_UX_ANALYSIS.md 要因E(サイロ)の根治につながる:
  ガレージを「Boardの一種」として同一エンジンに載せる長期オプションを確保

## 4. AIインポート — Markdown/貼り付け → 自動マス分類

### 4.1 パイプライン定義

```
入力(3経路)                     処理                         出力
────────────────           ─────────────────           ─────────────
a) Markdown貼り付け    →    1. 前処理(見出し/リスト        プレビュー画面
b) .mdファイル読込          構造のパース)                 (中枢候補+分類案)
c) URL指定(将来)      →    2. AI構造化(1コール)     →        ↓ ユーザー確認/編集
                            3. ローカルフォールバック      Boardツリー生成
                               (AIなし時)                  (source: "ai-import")
```

**AI構造化の出力契約**(既存 `ai-service.js` / `ai-providers.js` にJSONモードで追加):

```json
{
  "center": "この文書の中枢概念(1フレーズ)",
  "centerRationale": "なぜこれが中枢か(1文)",
  "groups": [
    { "label": "マスに入る要素(短文)",
      "items": ["元テキストの断片", "..."],
      "suggestChild": true }
  ],
  "overflow": ["どのマスにも属さない断片"],
  "suggestedPattern": "3x3"
}
```

- `groups` が8個を超える場合はAIに統合を指示しつつ、超過分は `overflow` へ —
  **切り捨てない**(overflowはBoardのmemoか1xN子Gridに退避し、必ず可視化する)
- `suggestChild: true` のグループは items を子Gridのセル候補として**2階層を一括生成**できる
  (深い文書 → 親3x3+子Grid数枚、が1回のインポートで立ち上がる)
- `centerRationale` をプレビューに表示 — 「AIがなぜ中枢と判断したか」を見せることが
  信頼と学習効果(ユーザー自身の思考訓練)につながる

### 4.2 プレビュー&確認UI(必須)

AI出力を**直接データに書かない**。プレビュー画面で:
- 中枢の差し替え(候補を3つまで出す/自分で書き直す)
- グループのドラッグでマス位置変更、統合、除外
- 確定で初めてBoard生成。`Cell.source = {type: "ai-import"}` を記録

これは Insight 実装済みの「確認画面→段階実行」パターン(`mandara-insight-controller.js:64-152`)
の流用であり、UIの新規性は低い。

### 4.3 ローカルフォールバック(APIキーなしでも動く)

AIなしでも成立させる(ADOPTION_UX_ANALYSIS.md ★7 と同じ思想):
- Markdownの**見出し階層をそのままツリーに写像**(H1=Board title、H2=セル、H3以下=子Gridセル)
- 中枢はH1 or 最頻出キーワード(既存 `mandara-local-analyzer.js` の語彙統計を拡張)
- 「構造はAIなし・中枢判定と再グルーピングだけAI」という段階利用も可能にする

### 4.4 URL読み込みの制約

ブラウザからの直接fetchはCORSで大半失敗する。既存の unfurl.io 依存(`js/url-converter.js:21`)と
同型の問題なので、**Vercel Functions の本文抽出プロキシ**(readability系)を1本立てるのが正道。
AIキーのサーバサイドプロキシ(★7)と同じFunctionに同居させると運用が1箇所に纏まる。
→ フェーズ上は「貼り付け/ファイル」を先行、URLは後続。

### 4.5 実現性評価

| 項目 | 評価 | 根拠 |
|---|---|---|
| Markdown貼り付け→AI分類 | **高** | 既存AI基盤(providers/rate-limiter/errors)がそのまま使える。プロンプト+スキーマ+プレビューUIのみ新規 |
| 2階層一括生成 | 高 | データモデルv2が前提。生成自体は純関数 |
| ローカルフォールバック | 高 | 見出しパースは正規表現レベル |
| URL読込 | 中 | サーバレス関数の新設が必要(小規模) |
| 精度リスク | 中 | 「中枢の誤判定」はプレビューUIで人間が最終決定する設計により致命傷にならない |

## 5. ビューモード — fit / canvas / whiteboard

### 5.1 モード定義

| モード | 定義 | レスポンシブ方針 |
|---|---|---|
| **fit** | 現行同様、1つのGridを1画面に収める | 従来通り縮小(小さいGrid向け) |
| **canvas** | Figma的な**パン/ズーム可能な無限平面**にGridツリーを配置。展開ビュー(§2.3)もここ | **無理に縮めない**。実寸で置き、スクロール/ズームで移動 |
| **whiteboard** | 枠なし。FreeNodeを好きな座標に置いて書き続ける半無限ページ | 同上 |

ユーザー指摘の通り、マスが多い/大きいモードをレスポンシブで縮めるのは誤り
(現に768px未満の3カラム維持で「1マスが小さくて入りきらない」— `js/mandara-view-prefs.js:3-4`)。
**「収める」のはfitモードの責務、「動き回る」のがcanvas/whiteboardの責務**と分離する。

### 5.2 canvas/whiteboardの実装アーキテクチャ

このプロジェクトはフレームワークなしのVanilla JS+SCSS。その前提での推奨構成:

```
<div class="canvas-viewport">            ← overflow:hidden、pointerイベント捕捉
  <div class="canvas-world"              ← transform: translate(x,y) scale(z)
       style="transform: ...">
    <div class="grid-widget" style="left:_px; top:_px">…3x3グリッド(既存DOM流用)…</div>
    <div class="free-node"   style="left:_px; top:_px">…contenteditable…</div>
  </div>
</div>
```

- **DOM+CSS transform方式**を採用(SVG/Canvas 2D描画は不採用)。理由:
  (1) セルは textarea/contenteditable による**リッチなテキスト編集**が主役 — DOMが圧倒的に有利
  (2) 既存のGrid描画・自動保存・IME対応(コミット cbfb21b で対応済み)をそのまま流用できる
  (3) Miro/Figma級の描画性能が必要になるのは数百ノード以降 — 個人の思考ツールでは
      当面到達しない。到達したら `content-visibility: auto` +ビューポート外の仮想化で延命
- 操作系: Pointer Events で pan(空白ドラッグ/Space+ドラッグ)、wheel+Ctrl で zoom、
  ピンチズーム対応(= `user-scalable=no` はcanvas系ページでは撤廃し、アプリ内ズームに一本化)
- カメラ状態は `Board.viewState.camera` に保存 — 「開いたら前回見ていた場所」が再訪体験を作る
- 外部ライブラリは原則不要だが、pan/zoomだけ `panzoom`(〜4KB)を使う選択肢はあり。
  依存を増やすなら**CDN直読みではなくバンドル**(ADOPTION_UX_ANALYSIS.md Phase5 の方針に合わせる)

**実現性: 中〜高。** 技術的な新規性はtransform管理と座標系(スクリーン⇄ワールド変換)のみ。
最初の実装は「Gridウィジェット1個+FreeNode」だけ動けばよく、段階的に載せられる。

### 5.3 whiteboard(半無限ページ)の振る舞い定義

- ダブルクリック(タップ)した位置に FreeNode 生成 → 即入力開始(**クイックキャプチャの理想形**)
- ノードはドラッグ移動、近接ノードの簡易スナップ(任意)、色ラベル
- 保存は既存デバウンス自動保存に FreeNode 配列を乗せるだけ
- **「構造化」への昇格導線**(whiteboardを一過性のお絵かきで終わらせない核):
  - 複数ノードを矩形選択 →「マンダラ化」→ AIが選択ノードを §4 と同じ契約で
    中枢判定+マス分類 → その場にGridウィジェット生成、元ノードは `source` 記録付きでセル化
  - 逆方向: Gridのセルを「ばらす」→ FreeNodeに分解して再発散
- これにより **発散(whiteboard)⇄ 収束(mandara)** が同一キャンバス上で往復可能になる。
  これがこの構想全体の最大の差別化点(単なる「マンダラアプリ+ホワイトボード併設」ではない)

### 5.4 モバイル

- fitモード: 1セル拡大編集(タップでフォーカスモード)— ADOPTION_UX_ANALYSIS.md ★6
- canvas/whiteboard: ピンチズーム+ドラッグはタッチと相性が良く、
  むしろ現行の「縮んだ9マス」より**モバイル体験は改善**する見込み
- 二本指パン/一本指ドラッグの衝突だけ要設計(ノードドラッグはロングプレス開始にする等)

## 6. 外部データとの相互運用(双方向)

| 方向 | 形式 | 内容 | 実現性 |
|---|---|---|---|
| In | Markdown貼り付け/.md | §4 AI分類インポート | 高 |
| In | URL | サーバレス抽出プロキシ経由 | 中 |
| In | JSON | Boardフルバックアップの復元 | 高 |
| Out | Markdown | **ツリー→見出し階層**の決定的写像(中心=H2、セル=箇条書き、子Grid=H3…)。Obsidian/Notionへそのまま貼れる | 高 |
| Out | JSON | Boardフルエクスポート(バックアップ不安の根治 — README-MODES.md:94-95 の「非対応」解消) | 高 |
| Out | 画像/SVG | canvasビューのスクリーンショット共有(後続) | 中 |

- **ラウンドトリップ保証**をテスト対象にする: `export(import(md)) ≒ md`(構造レベルで)。
  これが成立すると「Mandaraは外部メモ資産の一時的な思考ビュー」という位置づけが可能になり、
  ロックイン不安が消えて外部データを持ち込む心理障壁が下がる
- エクスポート実装は既存 `mandara-insight-export.js:268-301`(コピー/DL)の器を流用

## 8. リスクと対応

| リスク | 影響 | 対応 |
|---|---|---|
| `mandara.js`(951行・グローバル密結合)の改修コスト | M1が膨らむ | Store化を先行し、UIは段階移行。E2E(playwright)の既存mandara specを回帰ガードに |

| 機能過多で「9マスのシンプルさ」を失う | 思想の毀損 | デフォルトは現行同等のfit 3x3。展開/canvas/AIはすべて明示的アクションでのみ発動 |

## 9. まとめ — なぜこの順番か

- **M1(モデルv2)が全ての要**。セルを文字列からオブジェクトにしない限り、親子もキャンバスも
  AI分類も載らない。ここに投資すれば以降は独立に積める。
- **フラクタル(M2)は見た目より安い**。ツリー操作は純関数の世界で、81マスは「ビュー」として
  無償で導出される。体感価値(思考が無限に深掘れる)に対して工数が小さい、最も費用対効果の高い一手。
- **AIインポート(M3)は既存資産の再構成**。プロバイダ・レート制限・確認フローは実装済みで、
  新規はプロンプト契約とプレビューUIのみ。「外部データが入る」ことでMandaraを開く理由が日常側に増える。
- **canvas/whiteboard(M4/M5)は差別化の本丸だが最後**。上の3つが揃って初めて
  「発散⇄収束の往復」という他にない体験になる。単体で先行させると"ただの簡易Miro"で終わる。
